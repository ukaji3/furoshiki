# ADR 0002: リソースは重複排除したストアに置き、文書内にはプレースホルダを書く

- 状態: 採択
- 日付: 2026-09-23

## 背景

サイトの CSS / JavaScript / 画像 / フォントは多くのページから共有される。
各ページの HTML にそれらを直接インライン化(`<style>` 化、`<script>` テキスト化、
`data:` URL 化)すると、30 ページが同じ CSS とロゴを参照するサイトでは同じバイト列が
30 回出力に含まれる。また `<script src>` をテキストとしてインライン化する場合、
`</script` や `<!--` のエスケープが必要になり、正規表現リテラルや文字列の中に
それらが含まれるスクリプトを壊す危険がある。

## 検討した選択肢

### (a) ページごとにインライン化(初期案)

`<link rel=stylesheet>` → `<style>`、`<script src>` → インラインテキスト、
その他 → `data:` URL。重複排除はバイナリのみ。

- 単純だが、共有 CSS / JavaScript が参照ページ数だけ複製される。
- `defer` / `async` の意味を保つためにスクリプトを `</body>` 直前へ移動する必要があり、
  実行順序やタイミングが元と変わる。
- `</script` エスケープが必要で、スクリプト内容を書き換えるリスクがある。

### (b) 重複排除ストア + プレースホルダ + 表示時展開(採択)

参照先のファイルは **メディアタイプと内容の SHA-256** をキーにストアへ 1 回だけ格納し、
文書内の URL は `furoshiki-res:<16 桁 hex>` というプレースホルダに置き換える。
`<link href>` / `<script src>` / `<img src>` などの要素は **そのまま残し**、属性値だけを
プレースホルダにする。表示時にランタイムがプレースホルダを `data:` URL に展開する。

リソースは 2 種類に分ける。

- バイナリリソース: バンドル時に base64 の `data:` URL に変換して格納する。
- テキストリソース(CSS / JavaScript): UTF-8 テキストとして格納する。CSS の中の
  `url()` / `@import` もプレースホルダに書き換えられているため、ランタイムは
  テキスト内のプレースホルダを再帰的に展開してから
  `data:text/css;charset=utf-8,` + `encodeURIComponent(text)` を組み立てる。

- 長所
  - 共有リソースは 1 回だけ格納される(CSS / JavaScript も含めて)。
  - `<script src defer>` / `async` / `type=module` / `<link media>` / `disabled` /
    `onload` などの挙動はブラウザ標準のまま。スクリプトの移動もエスケープも不要。
  - 文書内の参照は URL の置換だけなので、変換が局所的で検証しやすい。
- 短所
  - `document.currentScript.src` や `import.meta.url` が `data:` URL になる。
  - `data:` URL のスクリプトで発生したエラーは、ブラウザによって詳細が抑制される
    可能性がある(未検証)。
  - ランタイム(JavaScript)が展開を行う前提になるが、ADR 0001 で JavaScript は既に必須。

## 決定

(b) を採択する。

## 詳細

- プレースホルダの構文は `furoshiki-res:([0-9a-f]{16,64})`。Go 側(`internal/store`)
  とランタイム(`internal/shell/shell.js`)が同じ正規表現を持ち、テストで一致を確認する。
- キーは SHA-256 の先頭 16 桁。同一ストア内で先頭一致の衝突が起きた場合のみ
  8 桁ずつ延長する(実質的に起きない)。同じ入力からは常に同じキーが得られるので
  出力は決定的である。
- リソースのフラグメント(`font.eot?#iefix`、`sprite.svg#view`)はプレースホルダの
  後ろに保持する。
- テキストリソースの展開結果はランタイム側でキャッシュし、循環参照は展開しない。
- `<use href="sprite.svg#id">` は `data:` URL では動かない(外部文書のフラグメント
  参照は同一オリジン要件により不可)ため、スプライト SVG を文書内に 1 回だけインラインし、
  `href="#id"` に書き換える。
- `--max-resource-size` を超えるファイルは格納せず、参照を元のまま残して警告する。

## 結果

- 出力サイズは「ページ HTML の合計 + 一意なリソースの合計」に近づく。
- スクリプトの内容は一切書き換えられない。
- ペイロードは `<script type="application/json">` に置き、`</` と `<!--` を
  JSON の等価なエスケープ(`<\/`、`\u003c!--`)に置換することで安全に埋め込む。
